# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

.NET 8 (C# 12) REST API for employee and document management ("People Management"). Uses Clean Architecture with Domain-Driven Design (DDD) and CQRS pattern via MediatR.

## Build, Run & Test

```bash
# Build
dotnet build

# Run API (from server/Services/PeopleManagement/PeopleManagement.API/)
dotnet run
# HTTP: localhost:5000 | HTTPS: localhost:5001 | Swagger: localhost:5001/swagger

# Run with Docker
docker-compose -f docker-compose.yml up --profile api

# Run all unit tests
dotnet test Services/PeopleManagement/PeopleManagement.UnitTests/

# Run all integration tests
dotnet test Services/PeopleManagement/PeopleManagement.IntegrationTests/

# Run a single test class
dotnet test --filter "FullyQualifiedName~ClassName"

# EF Core migrations (from PeopleManagement.API/)
dotnet ef database update --project ../PeopleManagement.Infra
```

### Certificado HTTPS de desenvolvimento (acesso pelo IP da LAN)

Em Docker a API é servida em `https://<ip>:8041` (8041→443). O dev-cert padrão do ASP.NET só tem SAN para `localhost`/`127.0.0.1`, então **acessar pelo IP da rede o Chrome bloqueia** (`ERR_CERT_COMMON_NAME_INVALID`). Um cert [mkcert](https://github.com/FiloSottile/mkcert) cobre esse caso.

- **Cert em uso:** `%APPDATA%\ASP.NET\Https\PeopleManagement.API.lan.pfx`, senha `changeit`, apontado explicitamente pelas envs `ASPNETCORE_Kestrel__Certificates__Default__Path/Password` no `docker-compose.override.yml`. O nome é `.lan.pfx` **de propósito**: o Visual Studio regenera/sobrescreve `PeopleManagement.API.pfx` (a convenção `Kestrel:Certificates:Development`) e apagaria o nosso. Config explícita `Certificates:Default` vence a convenção.
- **SAN não aceita wildcard de IP** — `192.168.15.*` é inválido em X.509, o match de IP é exato. A cobertura da faixa vem de listar os 254 IPs individualmente.
- **A pasta montada é `%APPDATA%\ASP.NET\Https`** (do override), não `%USERPROFILE%\.aspnet\https` (do `docker-compose.yml`) — os dois montam o mesmo destino e **o override vence**; confira com `docker compose --profile api config`.
- Regenerar (renovar, ou trocar a faixa quando o IP da rede mudar):

```bash
mkcert -install   # cria/instala a CA local no trust store do Windows (Chrome usa esse)
cd "$APPDATA/ASP.NET/Https"
# ajuste a faixa se a rede mudar; repita o -pkcs12 se precisar de outra sub-rede
mkcert -pkcs12 -p12-file PeopleManagement.API.lan.pfx \
  localhost 127.0.0.1 ::1 host.docker.internal $(seq -f "192.168.15.%g" 1 254)
```

Outras máquinas/celulares da rede não confiam nessa CA: instale nelas o `rootCA.pem` de `mkcert -CAROOT`. Certificado é só para desenvolvimento.

## Architecture

```
Services/PeopleManagement/
├── PeopleManagement.API/            # Controllers, auth, filters, DI setup (Program.cs)
├── PeopleManagement.Application/    # CQRS Commands & Queries, DTOs, FluentValidation validators
├── PeopleManagement.Domain/         # Aggregates, entities, value objects, domain events
├── PeopleManagement.Infra/          # EF Core DbContext, repositories, migrations, external service clients
├── PeopleManagement.Services/       # Domain event handlers
├── PeopleManagement.UnitTests/
└── PeopleManagement.IntegrationTests/
```

**Request flow:** Controller → MediatR dispatch → Command/Query Handler → Repository/Domain → DbContext

**CQRS:** Commands (writes) and Queries (reads) are separate, both dispatched via MediatR. Commands use `IdentifiedCommand<T>` wrapper for idempotency via `x-requestid` header.

**Domain:** Aggregates under `Domain/AggregatesModel/` — key ones: Employee, Document, Company, Department, Role, Position, Workplace, DocumentTemplate, RequireDocuments, DocumentGroup. Value objects: CPF, Name, Contact, Address, Image, etc.

**Document status (as definições canônicas):** só o `DocumentUnitStatus` é escrito; o do `Document`, o do grupo e o do funcionário são derivados dele, nessa ordem. Mexer numa definição aqui muda os quatro níveis.

| `DocumentUnitStatus` | Significado | Entra a partir de | Cobre a exigência? |
|---|---|---|---|
| `Pending` (1) | Falta entregar, nenhum arquivo ainda | criação da unidade | não |
| `RequiresValidation` (5) | Entregue, alguém precisa conferir se vale | `Pending` | não |
| `AwaitingSignature` (7) | Enviado ao funcionário, aguardando assinatura | `Pending` | não |
| `OK` (2) | Documento válido e vigente | `Pending`, `RequiresValidation` | **sim** |
| `Warning` (8) | Ainda válido, perto de vencer — providenciar substituto | `OK` | **sim** |
| `Expired` (9) | Venceu e **não há substituto entregue** | `OK`, `Warning` (job de vencimento) | não |
| `Deprecated` (3) | Saiu de vigência **e já tem substituto**; mantido como prova de que houve documento válido no período | `Expired` (chegou substituto), `OK`/`Warning` (depreciação manual ou policy de novo contrato) | histórico, neutro |
| `Invalid` (4) | Erro ou engano — **sem valor legal nenhum** | `RequiresValidation` (recusa), `OK`/`Pending`/`NotApplicable` (invalidação), pendente duplicada descartada | não |
| `NotApplicable` (6) | Não se aplica a este funcionário — exceção deliberada à regra | `Pending` | **sim**, igual a OK |

- **A distinção que sustenta tudo é `Expired` vs `Deprecated`**: as duas são saída de vigência, e o que as separa é existir substituto. Só `Expired` é problema de conformidade. Antes as duas eram o mesmo status e cada consumidor reconstruía a diferença do seu jeito (ou não reconstruía).
- **`Deprecated` e `Expired` nunca podem ser invalidados** (`PMD.DOC24`) — são a prova do período coberto, e apagá-la é justamente o que a definição de Deprecated existe para impedir. Depreciar exige vigência (`PMD.DOC23`).
- **Métodos com intenção explícita** em `DocumentUnit`: `MarkAsExpired` (só de OK/Warning), `MarkAsDeprecated` (de OK/Warning/**Expired**), `MarkAsInvalid` (de Pending/OK/RequiresValidation/AwaitingSignature/**NotApplicable**) e `Supersede` = deprecia se teve valor, descarta o que estava em curso. Substituíram o `MarkAsDeprecatedOrInvalid`, que decidia pelo status de origem em vez da intenção do chamador e por isso servia a três fluxos incompatíveis.
- **`NotApplicable` é invalidável, mas NÃO é superável.** Invalidar é como o documento **volta a ser exigido**: a dispensa é decisão administrativa, não prova de cobertura, então desfazê-la não apaga período nenhum — ao contrário de `Deprecated`/`Expired`, que continuam recusados. Mas isso vale só para a decisão explícita: `Supersede` chama `DiscardUndelivered` (Pending/RequiresValidation/AwaitingSignature), **não** `MarkAsInvalid`, justamente para que uma entrega qualquer não revogue a dispensa de carona — nem em `SupersedeUnitsCoveredBy` nem em `MakeAsDeprecated`. Reusar `MarkAsInvalid` ali é o erro que os testes `WhenAnotherUnitIsDelivered_NotApplicableUnitShouldSurvive` e `MakeAsDeprecated_ShouldNotDiscardNotApplicableUnit` travam.
- **`Document.Status` é derivado em UM caminho** (`RefreshDocumentStatus`): cada competência vira um status (`GetStatusFromGroup` — a melhor unidade define, `NotApplicable` cobre igual a `OK`) e o documento assume a pior por `DocumentStatus.Severity`. Documento sem competência é uma competência só. Havia dois ramos com precedências diferentes, e o ramo por competência descartava Deprecated e AwaitingSignature — documento periodizado com tudo vencido reportava OK.
- **`Severity` é a ÚNICA ordem** (pior → melhor): `Expired > RequiresDocument > RequiresValidation > AwaitingSignature > Warning > OK > Deprecated`. `Expired` é o pior porque é cobertura que caducou, contra `RequiresDocument`, que nunca foi cumprida. `Deprecated` é o **mais benigno, atrás de OK**: competência encerrada por substituição não tem nada a dizer, então só aparece quando é tudo o que existe — que é o caso de `MakeAsDeprecated` (documento inteiro fora de cena).
- **`Expired` → `Deprecated` acontece em `SupersedeUnitsCoveredBy`**, disparado por toda entrega (`InsertUnitWithoutRequireValidation`, `MarkAsValidDocumentUnit`, `MarkAsNotApplicableDocumentUnit`). O alcance normal é a competência da unidade que resolveu, com **duas exceções, ambas de qualquer competência**: toda unidade vencida (a renovação de um documento por competência cai na competência SEGUINTE, então exigir competência igual deixaria a vencida esperando um substituto que por construção nunca chega na dela); e a unidade que a que resolveu veio **substituir** (`ReplacesDocumentUnitId`) — sem ela, renovar ANTES do vencimento deixava a antiga viva (ainda `OK`/`Warning`, fora do alcance das outras duas regras) e o documento cobrava duas vezes a mesma coisa.
- **Um único rollup de conformidade** (`Domain/Services/DocumentStatusRollup.Summarize`) alimenta o status materializado do funcionário, o do grupo de documentos (`DocumentGroupQueries`) e o do documento exigido (`RequireDocumentsQueries`). Existiam duas implementações que **discordavam sobre `Deprecated`** — o funcionário aparecia Okay enquanto o grupo aparecia como problema, para o mesmo documento — e a do grupo ainda escrevia os ids 1/2/3 à mão em vez de usar `EmployeeDocumentStatus` (0/1/2), o que fazia o cliente rotular Warning como "Pendente". O `DocumentStatusUtil` foi removido.
- **Depreciar e invalidar sempre deixam uma pendente no lugar** (`DocumentService.DeprecateDocumentUnit` / `InvalidateDocumentUnit` → `ReplaceDocumentUnit`). A exigência continua de pé — vale também para a recusa de validação e para desfazer um `NotApplicable`, que sem isso deixava o documento **sem nenhuma ação possível na tela**. `NewDocumentUnit` reaproveita pendente equivalente, então chamar sempre é idempotente. Essa pendente é **correção**, não renovação: não consome cota (ver "Renovação").
- **Endpoints:** `PUT /document/DocumentUnit/deprecate` (`[ProtectedResource("document","deprecate")]` — **scope novo, precisa existir no Keycloak**), `PUT /document/DocumentUnit/invalid` (`reject`), `PUT /document/DocumentUnit/not-applicable` (`mark-not-applicable`), `POST /document/DocumentUnit/renew` (`create`). Regra de tela: depreciar só de `OK`; invalidar de `Pending`, `OK` ou `NotApplicable`; não aplicável só de `Pending`; renovar de `OK`, `Warning` ou `Expired`. O agregado é mais permissivo no invalidar porque o mesmo caminho serve à recusa de validação.
- **Migration `AddExpiredDocumentUnitStatus`**: coluna `ExpirationCount` (hoje `RenewalCount`, ver "Renovação") + backfill de `Deprecated` sem substituto → `Expired` (o mesmo predicado que o dashboard usava) + backfill do contador. `Invalid` **não** é convertido: entrava no bucket "Vencidos" do dashboard antigo, mas pela definição é erro, não vencimento.

**Renovação (`POST /document/DocumentUnit/renew`):** trocar uma entrega que está saindo de vigência por outra. É **decisão explícita do RH** — nenhum job cria unidade.

- **Vencer e avisar não criam nada.** `DocumentDepreciationService.WarningExpirateDocument` e `DepreciateExpirateDocument` só movem o status da unidade (`Warning` / `Expired`); antes o vencimento criava a substituta sozinho. Os dois **carregam a coleção INTEIRA de unidades** e **saem sem salvar quando não há transição** — com o `Include` filtrado pela unidade do job, o `RefreshDocumentStatus` recalculava o status do documento a partir de uma unidade só, e um job chegando sobre unidade já `Deprecated` deixava o **documento** `Deprecated` (que rola para `Okay` no funcionário, escondendo pendência aberta).
- **`DocumentUnit.ReplacesDocumentUnitId` é o vínculo substituta → substituída** (coluna nullable, sem FK; migration `AddReplacesDocumentUnitIdToDocumentUnit`, sem backfill). A relação sempre existiu de fato, mas era implícita, e três perguntas não tinham resposta: quem depreciar quando a substituta é entregue (podem estar em competências diferentes), se a renovação já foi pedida, e se uma pendente é cobrança ou renovação em voo. É de onde saem `Document.NewReplacementUnit` (é `NewDocumentUnit` + vínculo, logo herda o reaproveitamento de pendente equivalente) e `LiveReplacementFor` (substituta em curso ou já cobrindo; uma **descartada não conta**, para um engano não travar a renovação).
- **Renovação em voo não conta no status do documento** (`Document.IsRenewalInFlight`, aplicado em `RefreshDocumentStatus`): substituta `IsInFlight` cuja substituída ainda `CoversRequirement` sai do agrupamento. Sem isso, renovar um documento `Warning` o **piorava** — a substituta nasce noutra competência (a mínima, esperando data) e virava competência descoberta, levando o documento de "A Vencer" para "Falta Entregar". Renovar no prazo não pode deixar o documento pior do que ignorar o aviso. Quando a substituída vence ela deixa de cobrir, a substituta volta a contar, e o documento fica `Expired` até a nova ser entregue — exatamente o que o status comunica.
- **`Document.RenewalCount` conta renovações EMITIDAS, não vencimentos** (era `ExpirationCount`; migration `RenameExpirationCountToRenewalCount`, o valor legado é bom porque vencer renovava automaticamente). Só `RegisterRenewal` incrementa; `ExpireDocumentUnit` não mexe mais. Contar vencimento errava dos dois lados depois que renovar virou decisão: renovar antes do prazo nunca vencia a unidade e portanto **nunca consumia cota** — um teto de N renovações renovaria para sempre —, e um documento vencido e abandonado queimava a cota sem nenhuma renovação ter existido. Depreciar/invalidar **não** passam por `RegisterRenewal`: são correção, não troca de ciclo.
- **`DocumentService.RenewDocumentUnit` é onde a decisão mora** (cruza dois aggregates: cota no template, contador no documento). Ordem: idempotência primeiro (`LiveReplacementFor` devolve a mesma substituta sem consumir cota de novo — duplo clique ou retry), depois `IExpirationPolicy.CanRenew(RenewalCount)` (sem policy renova sempre), depois `NewReplacementUnit` + `RegisterRenewal`. A substituta nasce **sem data de referência** (competência mínima, esperando a real) e com a configuração ATUAL do template. `DocumentUnit.CanBeRenewed` = `OK`/`Warning`/`Expired` (`PMD.DOC25`); teto esgotado é `PMD.DOC26`.
- **Escopo `create`, não um novo:** renovar é criar a próxima unidade do documento, mesmo escopo do `POST /document`. Um escopo novo obrigaria a mexer no Keycloak por uma permissão que já existe com o mesmo significado.
- **`DocumentQueries.GetById` ordena pendentes sem data primeiro** (`Date == MinValue` desc, depois `Date` desc). Unidade recém-criada nasce com `Date = DateOnly.MinValue`; ordenando só por data decrescente ela caía na **última página** e a substituta recém-pedida sumia da tela num documento com histórico.
- **Cobertura:** `DocumentUnitExpiredStatusTests` (unitário: contador, vínculo, status com renovação em voo, depreciação da substituída na entrega, idempotência do `LiveReplacementFor`) e `DocumentExpirationRenewalTests` (integração: jobs não criam nada, a regressão do `Include` filtrado, renovação antes/depois do vencimento, idempotência, e o teto sendo respeitado **mesmo renovando sempre antes de vencer** — a regressão que motivou trocar o contador).
- **Excluir documento também recalcula o status do funcionário** (`IEmployeeDocumentStatusRefresher`, chamado por `RequiresDocumentsEventHandler`): deletar não dispara `DocumentStatusChangedDomainEvent`, e sem isso o funcionário ficava "requer atenção" por causa de um documento que deixou de ser exigido. `GetAllStatusByEmployeeAsync` ignora os documentos marcados como `Deleted` no change tracker pela mesma razão que já lia os `Modified` em memória.

**DocumentTemplate policies:** `DocumentTemplate` composes an opt-in set of rules (`Policies/`) instead of one nullable field per rule — **presence in the set = rule active**. Consumers read by capability (`GetPolicy<IExpirationPolicy>()`), never off the raw fields. A new rule is a new class, not a new column.

- **Capabilities:** `IExpirationPolicy` (validity + `CanRenew`), `IWorkloadPolicy`, `IPeriodPolicy`, `ISignaturePolicy`, `INewContractDeprecationPolicy`, all under the `IDocumentPolicy` marker. `PolicyType` is the smart-enum discriminator.
- **Expiration is two policies under one capability.** `ExpirationPolicy` renews forever (`CanRenew(_) => true`); `ExpirationLimitedPolicy(Duration, MaxRenewals)` renews `MaxRenewals` times then stops (`CanRenew(count) => count < MaxRenewals`, onde `count` é `Document.RenewalCount`). Both share `PolicyType.Expiration` — the discriminator between them is `ExpirationParams.MaxRenewals` (`int?`): **null = forever, present = limited**. So rows written before the limited variant (and the backfill) rehydrate as `ExpirationPolicy` with no data migration. `ToPersistence` must match `ExpirationLimitedPolicy` **before** `IExpirationPolicy` — matching by the interface would drop `MaxRenewals`. Limited invariants: `Duration > 0` (`PMD.DOCT11`) and `MaxRenewals >= 1` (`PMD.DOCT12`). **`DocumentService.RenewDocumentUnit` consumes it** (ver "Renovação"): gates renewal on `CanRenew(document.RenewalCount)` before issuing the replacement, e `RegisterRenewal` incrementa depois. No policy ⇒ renews forever (back-compat). **The counter is a column on `Document`, not a count of units by status**: any status-based count breaks, because the expired unit becomes `Deprecated` once the replacement arrives and supersession (re-upload/re-validation) also deprecates — correcting a document would consume a renewal. `DocumentService.ValidityDurationFor` reads the same policy at update time and gives the unit **no validity once the cota is exhausted**, so the last unit stays OK indefinitely instead of expiring with nobody allowed to renew it.
- **Signature is a policy.** Presence of `SignaturePolicy` = the template accepts signature, and it **carries the placements** — so a placement without acceptance is unrepresentable in the persisted model. `AcceptsSignature` and `PlaceSignatures` are derived getters (`Ignore`d in EF); there is no `AcceptsSignature` column and no `PlaceSignature` table. **The signature always comes from the `acceptsSignature`/`placeSignatures` parameters, never from the `policies` set** — the API sends it separately, so letting the set drive it would wipe the signature on every Edit carrying only the other rules. The old contradiction check survives at that parameter boundary (`SetSignature`), which is the last place the two can disagree. **Read and write contracts differ for signature, on purpose.** The **write** takes `acceptsSignature` + `placeSignatures` as top-level parameters (the domain reads them there, never from the `policies` set). The **read** (`GET`) is standardized: signature is a block inside `policies` — `policies.signature` present = accepts, and it **carries the placements** (`SignaturePolicyDto.PlaceSignatures`), mirroring every other rule. `DocumentTemplateQueries.ToPoliciesDto` sources it from `GetPolicy<ISignaturePolicy>()`, independent of `TemplateFileInfo` — so a template that accepts signature without a file still returns its placements. The placements are **not** on `TemplateFileInfoDto` anymore (they were, and gating that block on `TemplateFileInfo != null` dropped signatures on GET). Top-level `AcceptsSignature` stays on the DTO (back-compat + the `simple` list endpoint), consistent with `policies.signature`'s presence.
- **New-contract deprecation is a parameterless policy.** `NewContractDeprecationPolicy` (`PolicyType.NewContractDeprecation` = 6) has **no fields** — presence is the whole rule, and its jsonb `Params` is `{}` (written from an empty record so a future parameter lands without changing the discriminator; `ToPolicy` never reads it back). **The trigger is `CompleteAdmission`**, the only path that opens an employment contract (`Employee.NewContract` is private and only it calls). `EmployeeEventHandler` gates on `EmployeeEvent.COMPLETE_ADMISSION_EVENT` and calls `IDocumentDepreciationService.DeprecateDocumentsForNewContract` **before** `CreateDocumentUnitsForEvent`, so the document reaches its final state before generation adds the new contract's pendings. The rule crosses two aggregates (template decides, document mutates), so it lives in the service, not in `Document`; the policy is read **live**, so editing the template applies from the next admission on.
  - **`Document.DeprecateDeliveredUnits()` is the aggregate side.** Delivered = `OK`, `Warning` **or** `Expired` — Warning is an OK unit that is expiring (`MarkAsWarning` only fires from OK), so leaving it alive would carry a previous-contract document across and let the expiration job renew it under the wrong contract; Expired is delivery of the previous contract too, and the new contract generates its own pendings, so it stops being an open charge. Pending / AwaitingSignature / RequiresValidation are still in flight and survive; Deprecated / Invalid / NotApplicable are already out. Unlike `MakeAsDeprecated`, which supersedes everything. It returns the count and is idempotent (a second admission counts 0).
  - **Loads ALL units.** The service `Include`s the whole `DocumentsUnits` collection because `DeprecateDeliveredUnits` calls `RefreshDocumentStatus`, which scans the collection — a partial load would make it lie. It also does **not** `SaveChanges`: it runs inside domain-event dispatch, which happens *before* the triggering UoW's `SaveChangesAsync`, so saving there would re-dispatch the queued events.
  - **A deprecated unit next to a fresh pending leaves the document `RequiresDocument`** — deprecated means "already superseded", and here the substitute is precisely the new contract's pending; what is left to do is deliver it. Different from an **expired** unit with no substitute, which leaves the document `Expired`.
  - **Contract:** `newContractDeprecation` is an empty block on Create/Edit (`{}` = on, omitted = off) and on the read DTO. Listed by `GET /documenttemplate/PolicyType`.
- **Zero is absence, not a rule.** Policy constructors reject a non-positive duration (`PMD.DOCT11`) — a rule that expires nothing is absence wearing a rule's clothes, and the Composite reads presence as "active". Three places must agree: the constructor throws, `SyncPoliciesFromFields` **skips** (legacy rows store `00:00:00` and must not blow up on edit), and the migration backfill filters `> INTERVAL '0'`. Break one and templates either grow phantom rules or fail to rehydrate.
- **Persistence:** owned collection → child table `DocumentTemplatePolicies` (`Type` int + `Params` jsonb). `DocumentPolicyFactory` (de)serializes; durations travel **in ticks** so the migration backfill can reproduce the payload in SQL.
- **Source of truth:** `Create`/`Edit` accept an optional policy set. Informed → policies win and the legacy scalars (`DocumentValidityDuration`, `Workload`) are mirrored from them. Omitted → legacy path, policies derived from the scalars. The scalars are **kept and deprecated**; the read model still reads them.
- **API contract:** optional `policies` block per rule (`expiration`, `workload`, `period`) on Create/Edit — omit for legacy behavior, `{}` for no rules. The `expiration` block carries `durationInDays` + optional `maxRenewals` (`int?`): omit/null → `ExpirationPolicy` (renews forever), present → `ExpirationLimitedPolicy` (renews N times). The read DTO (`ExpirationPolicyDto`) echoes `maxRenewals` back (null for forever). The `period` block carries `periodTypeId` + `usePreviousPeriod`; a present block sets the `PeriodPolicy`, and `SyncFieldsFromPolicies` mirrors `usePreviousPeriod` into the legacy scalar. `GET /documenttemplate/PolicyType` lists the supported rules; `GET /documenttemplate/PeriodType` lists the competência granularities for the UI dropdown.
- **`IPeriodPolicy` drives competência — read LIVE from the template, never copied.** "Template é a configuração, a unit é a história": every operation reads the template's `PeriodPolicy` at that moment and passes **values** (`PeriodType?`, `usePreviousPeriod`) into the aggregate methods (`NewDocumentUnit`, `UpdateDocumentUnitDetails`, `DocumentUnit.Create/SetPeriod/UpdateDetails`) — never the template entity (aggregate boundary). There is **no** `Document.PeriodType`/`UsePreviousPeriod` column (dropped by `RemovePeriodConfigFromDocuments`, no backfill needed — legacy docs work as soon as the template has the policy, which `DeriveDocumentTemplatePeriodPolicies` backfilled). Editing the template takes effect **immediately** for the next operations on every document; competências already stamped on units are per-unit history and never move by themselves. This mirrors how expiration/workload/signature were always consumed (live at update/expiration/send time) — period used to be the lone frozen copy. The event only triggers generation and supplies "now" as the reference date.
  - Callers that create units must have the template in hand: `DocumentService` (both generation flows load ALL involved templates, not just the ones without documents), `DocumentDepreciationService` (renewal), `SignDocumentService.InvalidateSessionDocuments` (replacement units, batch-loads the session's templates), `BatchCreateDocumentUnitsCommandHandler`. The read DTO's `UsePreviousPeriod` now comes from the template join (`DocumentQueries`), same wire contract.
  - `DocumentUnit.Create`/`NewDocumentUnit` take the period config + an optional `referenceDate`: with a date, the unit lands in that competência; **without a date, it lands in `Period.CreateMinimum` (year `MIN_YEAR` = 1900)** — a placeholder replaced when a real date arrives via `UpdateDetails`. `CreateMinimum` ignores `UsePreviousPeriod` on purpose (there is no period before the floor; computing "previous" there would underflow).
  - **Minimum-period pendings survive granularity changes.** When the candidate period is the minimum and no exact match exists, `NewDocumentUnit` reuses ANY pending sitting at `MIN_YEAR` regardless of its (old) granularity and re-situates it via `ResetPeriodToMinimum` — otherwise editing Monthly→Yearly would orphan the waiting pending and create a duplicate. `UpdateDetails` with a period config also **situates units that had no period yet** (legacy docs heal on their next date update); without a config, existing periods are left untouched (history).

**Document content snapshot (`Content` da unidade):** o `DocumentUnit.Content` é um **snapshot** dos dados (empresa, funcionário, cargo, …) tirado no `UpdateDocumentUnitDetails` e consumido depois por `GeneratePdf`/`GeneratePdfRange` e pelo fluxo de assinatura (`SignDocumentService` chama `GeneratePdf`). Como o cadastro muda com o tempo, o snapshot envelhece em silêncio — daí a verificação abaixo.

- **`IDocumentContentBuilder` é a ÚNICA definição do formato** (`Services/DocumentContentBuilder.cs`). Gravação e verificação passam por ele, para que a comparação seja contra uma string produzida exatamente do mesmo jeito. Recebe **valores** (`recoverDataTypes`, `date`, `validity`, `workloadEndDate`), nunca o `DocumentTemplate` — não cruza fronteira de aggregate. Mexer no formato aqui muda PDFs em produção; `DocumentContentOutdatedTests` tem a regressão que pega isso (grava pelo update e confere que o check imediatamente seguinte não acusa divergência).
- **Comparação é `string.Equals(..., Ordinal)` contra o `Content` cru** — sem normalizar, reserializar ou converter. O merge de `JsonObject` preserva ordem de inserção e nunca muta as fontes, então mesma entrada ⇒ mesma string.
- **As datas vêm da unidade, não do template.** `CheckOutdatedContent` alimenta o builder com `unit.Date`/`unit.Validity`/`unit.WorkloadEndDate` já gravados. Recalcular a carga horária exigiria `VerifyTimeConflictBetweenDocument`, que escreve e lança — inaceitável num caminho de leitura. Consequência deliberada: o check enxerga **divergência de dado recuperado**, não mudança de regra do template (se a validade do template mudou, o check não acusa; o refresh corrigiria).
- **Falha ao recuperar ⇒ indeterminado, nunca "desatualizado".** `RecoverInfoToDocument` sempre pulou o tipo que falha, então o bloco sai ausente do JSON — indistinguível de um dado que mudou. O builder devolve `FailedTypes`; havendo qualquer falha o item volta `CheckFailed = true` com `IsOutdated = false`, para não empurrar o usuário a sobrescrever conteúdo bom por causa de um erro transitório.
- **Memo por (funcionário, tipo de dado)** dentro do builder (scoped ⇒ vale a request). Lotes repetem o mesmo par dezenas de vezes; dado de funcionário não muda no meio da request.
- **Endpoints** (`DocumentController`, ambos com body `{ items: [{documentUnitId, documentId, employeeId}] }`): `POST /document/content/check-outdated` (`[ProtectedResource("document","generate")]`, leitura pura — sem `IdentifiedCommand`, sem `SaveChanges`) devolve `{ items: [{documentUnitId, isOutdated, checkFailed}] }`; `POST /document/content/refresh` (`[ProtectedResource("document","edit")]`, com `IdentifiedCommand`) regrava o snapshot reusando `UpdateDocumentUnitDetails` **com a data já gravada** na unidade — renovar nunca move a data do documento, e só vale para unidade `Pending` (mesma guarda da geração). O refresh existe em vez de reaproveitar `PUT /document/DocumentUnit` justamente para o cliente não precisar reenviar a data (round-trip de formatação erraria a data do documento).

**Scheduled signature send (agendar envio para assinatura):** além de enviar agora (`POST /document/generate/send2sign`), o RH pode escolher **a data em que o documento sai** para o funcionário assinar — o caso de renovação, em que o substituto só deve chegar no dia em que o documento vigente vence.

- **O agendamento é um VO owned na unidade**, não colunas soltas: `ScheduledSignature` (`SendOn`, `DateLimitToSign`, `ReminderEveryNDays`) em `DocumentAggregate/ScheduledSignature.cs`, mapeado por `OwnsOne` em `DocumentUnitMap` (migration `AddScheduledSignatureToDocumentUnit`, só colunas nullable). **Presença = agendado.** Os três juntos porque data de envio sem prazo é um agendamento que o disparo não consegue executar. Invariantes: `SendOn >= hoje` (**`PMD.DOC21`** — hoje é aceito, sai no mesmo dia) e `DateLimitToSign > SendOn` (**`PMD.DOC22`** — o prazo conta a partir do envio; anterior nasceria vencido e o `InvalidateUnsignedDocument` mataria a unidade antes de o funcionário assinar).
- **A unidade continua `Pending` enquanto agendada** — agendamento é intenção, não envio. Nenhum status novo foi criado (seria invasivo no dashboard, no `GetStatusFromGroup` e no mapa 1–8 do cliente); a UI mostra um chip a partir de `DocumentUnitDto.ScheduledSignatureSendOn`.
- **Só o caminho "gerar e enviar" é agendável.** Agendar upload exigiria guardar os bytes no S3 até a data. Efeito colateral bom: o PDF é montado **no disparo**, então sai com o snapshot mais recente — por isso o cliente **não** passa o aviso de conteúdo desatualizado ao agendar (avisar sobre um dado que ainda vai mudar seria informação errada).
- **`Document.ScheduleSignatureSend` / `CancelScheduledSignatureSend`** são a porta de entrada. Agendar exige unidade `Pending` (`PMD.DOC15`) e não `AwaitingSignature` (`PMD.DOC14`). **Reagendar substitui** o VO; cancelar sem agendamento é **no-op** (idempotente).
- **Disparo:** `DocumentUnit` emite `ScheduleDocumentSignatureSendEvent`, e `ScheduleDocumentSignatureSendHandler` agenda o job Hangfire — o domínio não conhece o agendador, mesma divisão do `ScheduleDocumentExpirationHandler`. Roda às **09:00 no fuso de `TimeZoneOptions`**, não 05:00 UTC como a depreciação: este disparo notifica o funcionário (WhatsApp/SMS), e 05:00 UTC são 02:00 no Brasil.
- **`SignDocumentService.SendScheduledDocumentToSign(unitId, docId, companyId, expectedSendOn)` nunca lança** — caminho de job, loga e desiste (estilo `DocumentDepreciationService`), senão viraria retry infinito. Desiste quando: documento/unidade sumiu; o VO foi cancelado; a unidade não é mais `Pending` (aí **limpa o VO**, para a UI parar de anunciar um envio que não vai acontecer); ou **`SendOn != expectedSendOn`**. Esse último é como o **reagendamento invalida o job antigo** que continua na fila, sem rastrear job id do Hangfire. Seguindo em frente, delega ao `GenerateDocumentToSign` existente com os valores gravados — zero duplicação da lógica de assinatura.
- **Data sugerida:** `DocumentDto.SuggestedSignatureScheduleDate` = **MAX(`Validity`) entre as unidades OK e Warning**, e só quando `>= hoje`. Maior, e não menor: num documento por competência há várias entregues, e o que interessa é quando a última deixa de valer. É **calculada antes do filtro de `DocumentUnitParams.StatusId`** — filtrar a lista por "Pendente" tiraria a unidade OK da consulta e a sugestão sumiria da tela. Vem do servidor porque a lista de units na tela é **uma página**, e a unidade OK pode estar em outra.
- **Endpoints** (`DocumentController`, ambos com `IdentifiedCommand` e o escopo do envio imediato `[ProtectedResource("document", ["generate","send2sign"])]`): `POST /document/schedule/send2sign` (`{documentUnitId, documentId, employeeId, sendOn, dateLimitToSign, eminderEveryNDays}` — datas puras `yyyy-MM-dd`, diferente do envio imediato que manda instante ISO) e `POST /document/schedule/send2sign/cancel`.
- **Cobertura:** `DocumentScheduledSignatureTests` (unitário) e `ScheduleDocumentToSignTests` (integração: agendar/cancelar, a sugestão sobrevivendo ao filtro de status, e os três caminhos de desistência do disparo). O disparo bem-sucedido bate na ZapSign e fica de fora — mesmo motivo dos `Skip` em `DocumentTests`.

**Document dashboard (read model):** `api/v1/{company}/document-dashboard` (`GET /summary` + `GET /units`, both `[ProtectedResource("document","view")]`) serves the client's company-wide document dashboard from `DocumentDashboardQueries` (`Application/Queries/DocumentDashboard/`). Units are classified into five mutually-derived buckets — Expired, Expiring, Pending, AwaitingSignature, RequiresValidation — and summary counts and the paginated list share the SAME predicate per bucket, so they can never disagree. Semantics worth preserving: **Expired** = units in `DocumentUnitStatus.Expired`, plus OK/Warning units whose `Validity` is already past (covers the gap between the validity date and the depreciation job). The first half used to be a correlated subquery reconstructing "Deprecated/Invalid without a resolved substitute in the same period group" — the status now persists exactly that, so the bucket can no longer disagree with the document's and the employee's status. `Invalid` left the bucket on purpose: it is an error, not an expiry, and it surfaces through the replacement pending unit that invalidating creates. **Expiring** = OK/Warning with `Validity` within `expiringInDays` (query param, default 30) of "today" computed in the configured `TimeZoneOptions` zone. **Pending** = unidades `Pending` **exceto a renovação em voo** — substituta (`ReplacesDocumentUnitId`) cuja substituída ainda está `OK`/`Warning`/`NotApplicable`: essa não é falta, o documento já aparece em "A Vencer" pela substituída, e contá-la faria o número de Pendentes subir a cada renovação pedida no prazo, punindo quem age cedo. Quando a substituída vence ela deixa de cobrir e a renovação passa a contar normalmente. A substituída entra na consulta por um **LEFT JOIN** em `BuildRows` (`DashboardRow.Replaced`), não por subconsulta correlacionada: subconsulta comparando o smart enum de status **não traduz** no EF — a mesma armadilha que já custou erro em runtime na `BatchDocumentQueries`. Filters: employee status/name, document group, document template. Ordering: validity ascending (nulls last) for Expired/Expiring, unit date for the rest. Covered by `DocumentDashboardTests` (integration).

**Batch document (read model):** `api/v1/{company}/batch-document` (`GET /pending-units` + `GET /missing-employees`, ambos `[ProtectedResource("document","view")]`) alimenta a tela de documentos em lote a partir de `BatchDocumentQueries`. **Grupo, template e funcionário são três filtros independentes** (`documentGroupId`, `documentTemplateId`, `employeeId` — query params opcionais e combináveis): só funcionário atravessa grupos e templates ("tudo que falta do Fulano"), só grupo pega todos os templates dele, e nenhum devolve as pendências da empresa inteira. O template **era segmento de rota** (`/pending-units/{documentTemplateId}`) e por isso era obrigatório; o cliente contornava com fan-out de N requisições, uma por template, **somando o `TotalCount` de cada uma** — paginação que nunca fechou. A rota antiga saiu.

- **A ordenação desempata até o fim** (`emp.Name → template.Name → unit.Date → unit.Id`). Sem template fixo a lista mistura documentos, e ordenar só por nome deixa as unidades do mesmo funcionário em ordem arbitrária entre páginas — o suficiente para uma linha aparecer duas vezes ou sumir.
- **A linha carrega a identidade do documento** (`DocumentTemplateId`, `DocumentTemplateName`, `DocumentGroupName`): com a lista multi-template, dizer só o nome do funcionário não identifica o que está pendente. `IsSignable`/`CanGenerateDocument` sempre foram por linha — é o que permite ao cliente decidir a ação pela seleção em vez de pelo primeiro item.
- **`missing-employees` exige grupo ou template** e devolve **uma linha por par funcionário × template faltante** (`EmployeeMissingDocumentDto` carrega o template). Sem escopo o alcance seria "todos os templates da empresa", que não é operação válida — devolve vazio. Antes deduplicava por funcionário e perdia de qual template a pendência faltava, o que obrigava o cliente a criar para o grupo inteiro.
- **Duas armadilhas de tradução do EF** nessa query, ambas já custaram erro em runtime: `!DocumentsUnits.Any(u => u.DocumentId == doc.Id && u.Status == Pending)` **não traduz** (subconsulta correlacionada com o conversor do smart enum) — os ids saem materializados antes e viram `Contains`; e `Distinct()` seguido de `OrderBy` sobre a projeção também não traduz — ordena-se antes de projetar e deduplica em memória por (funcionário, template).
- Coberto por `BatchDocumentTests` (integração): cada eixo isolado, as combinações, a identidade do documento na linha, paginação de 1 em 1 sem repetir unidade, e os dois modos de `missing-employees`.

**Database:** PostgreSQL via EF Core 9 (Npgsql). Schema: `people_management`. Unit of Work pattern implemented in `PeopleManagementContext`. Domain events are dispatched during `SaveEntitiesAsync`.

**Auth:** Keycloak JWT Bearer tokens. Custom `[ProtectedResource("resource", "action")]` attribute for route-level authorization. Auth config in `PeopleManagement.API/Authentication/` and `Authorization/`.

**API routes:** All follow `/api/v1/{company}/{resource}` pattern. The `{company}` segment scopes operations to a company.

## Key External Integrations

- **Document Signing:** ZapSign API (with webhook callbacks at `/document/insert/signer`)
- **File Storage:** S3-compatible (Garage.io) via AWS SDK
- **Background Jobs:** Hangfire with PostgreSQL storage. Dashboard at `/hangfire`. Two queues: `default` and `whatsapp` (serial, 1 worker). The two `AddHangfireServer` (workers) in `Program.cs` are gated off when `ASPNETCORE_ENVIRONMENT == "IntegrationTest"` — storage/client stay registered, but no job is processed (determinism in tests).
- **PDF Generation:** PuppeteerSharp (requires Chrome/Chromium — bundled in Docker)
- **WhatsApp:** Evolution API for messaging
- **Timezone:** `E. South America Standard Time` (Brazil)

## Integration Tests

`PeopleManagement.IntegrationTests` runs against real containers via Testcontainers (Postgres + LocalStack for S3). Setup notes:

- **Shared fixture:** `PeopleManagementWebApplicationFactory` is a single **`ICollectionFixture`** (`IntegrationTestCollection`) for the whole suite — one set of containers, and all test classes share it. Because they live in one collection, xUnit runs them **serially**.
- **Isolation:** `BaseIntegrationTest` (base of every test class) resets the `people_management` schema via **Respawn** in `DisposeAsync` after each test. Tests seed their own data; there is no shared seed between tests. The reset also disposes the `IServiceScope`s handed out by `_factory.GetContext()`.
- **Shared helpers (`BaseIntegrationTest`):** reuse these instead of re-inlining boilerplate — `GetContext()`/`CreateClient()`; `PdfMultipartContent(params (name,value)[])` (multipart with the sample PDF under `formFile`); `GetDocumentAsync(id)` (fresh scope + `AsNoTracking` + `Include(DocumentsUnits)`); `AssertBlobExistsAsync(name, companyId)` (S3 download > 0 bytes).
- **Seeding:** data is built through the EF Object Mother extensions in `Data/PopulateDataBase` (`InsertCompany`, `InsertEmployeeActive`, `InsertDocument`, …) — seed through the domain factories, not raw SQL.
- **Environment `IntegrationTest`:** the factory sets `UseEnvironment("IntegrationTest")`, which (a) gates off the Hangfire workers in `Program.cs` and (b) skips `PopulateDb` (clean baseline). Jobs are only scheduled in storage, never processed.
- **Auth** is mocked (`MockAuthenticationHandler` + `MockAccessRequirementHandler`); `ConfigsUtils.InputHeaders(companies, authorization, xRequestId)` sets the request headers — `companies` goes as a single comma-separated value (what the handler `Split(',')`s), and a deterministic `xRequestId` can be passed to exercise `IdentifiedCommand` idempotency.
- **PDF templates:** the `CopyTemplatesToAppFiles` MSBuild target copies `DataForTests/templates/**` to `app_files/templates/**` in the output, where `PdfService` reads them (`DocumentTemplatesOptions:SourceDirectory`).
- **Skipped tests** depend on external ZapSign API/URLs or on an active Hangfire worker (incompatible with the deterministic setup) — see the `Skip` reasons.
- **Snapshot coverage:** `DocumentContentOutdatedTests` (funcionário intocado ⇒ não desatualizado — que é também a regressão de formato byte a byte do `IDocumentContentBuilder`; contato alterado ⇒ desatualizado; unidade sem `Content` ⇒ nada a avisar; lote misto marca só a alterada; refresh regrava o snapshot e preserva a data; unidade não-pendente é recusada no refresh). O template do seed usa **só** `RecoverDataType.Employee`: tipos que falham ao recuperar (PGR sem dado) marcariam a verificação como inconclusiva.
- **Policy full-cycle coverage:** `DocumentPeriodLifecycleTests` (competência after birth: minimum→real via update, `UsePreviousPeriod`, period moves with the date, duplicate-pending invalidation, template-edit applies to the NEXT operations — live read, not freeze), `DocumentPeriodLiveReadTests` (granularity change reuses+resituates the minimum-period pending instead of orphaning it, a document born before the template had a `PeriodPolicy` heals on its next update, delivered units keep their recorded periods), `DocumentUnitDetailsPolicyTests` (expiration→`Validity`, workload→`WorkloadEndDate`/working-day guard, and the absent-policy counterpoints), `SignDocumentPolicyGuardTests` (unsignable template rejected before any external call), `DocumentPolicyFullCycleTests` (all four policies composed: generate→update→OK→expire→**renew by hand**-at-minimum-period→expire→stop at the renewal cap), `NewContractDeprecationPolicyTests` (real dismissal→readmission through the endpoints: the delivered unit of the template *with* the rule is deprecated and a fresh pending is generated, the one *without* it survives OK, and an in-flight pending is untouched). Note: `DocumentUnit.Validity`'s setter rejects past validity, so expiration scenarios must anchor dates on "today" — fixed 2024 dates only work for templates without an expiration policy.
